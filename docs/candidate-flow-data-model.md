# WelHire Candidate Flow: Data Model and API Design

Status: design only. No production API or database integration is included yet.

## 1. Scope

This model supports the complete journey:

```text
Guest session
  -> CV upload
  -> CV parsing
  -> role and preference answers
  -> CV analysis and score
  -> login
  -> guest data merge into candidate account
  -> interview setup
  -> interview answers/transcript
  -> interview analysis
  -> profile history
```

The frontend can use the same contracts with a mock repository first. Later, the repository implementations can be replaced with Java service/API calls without changing the screen components.

## 2. Core identifiers

Every record must use a stable ID generated by the owning service. Do not use email or file name as a primary key.

| Identifier | Purpose |
|---|---|
| `guestSessionId` | Anonymous browser journey before login |
| `candidateId` | Permanent candidate profile |
| `userId` | Authentication identity; one candidate account owns one user |
| `cvDocumentId` | Uploaded CV and its parsing lifecycle |
| `cvAnalysisId` | Score and findings for one CV against one role |
| `interviewSessionId` | One interview attempt |
| `interviewAnswerId` | One answer in an interview |
| `interviewAnalysisId` | Feedback generated for one interview |

Recommended format: UUID/UUIDv7 strings. Every entity also has `createdAt` and `updatedAt` in UTC.

## 3. Database relationship

```text
User 1 -------- 1 Candidate
                    |
                    +---< GuestSession
                    +---< CvDocument
                    |        +---< CvParseResult
                    |        +---< CvAnalysis
                    +---< InterviewSession
                             +---< InterviewAnswer
                             +----- 1 InterviewAnalysis
                    +---< CreditTransaction
```

A guest session may exist without a user. When the guest logs in, the session is attached to the candidate and its records are linked to that candidate in a single merge operation.

## 5. Relational database design

The production database can use PostgreSQL. JSONB is intentional for parser output and evolving analysis payloads; searchable primary fields remain normalized.

```sql
create table app_user (
  id uuid primary key,
  email varchar(320) not null unique,
  display_name varchar(160) not null,
  initials varchar(8) not null,
  auth_provider varchar(30) not null,
  status varchar(20) not null default 'active',
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table candidate (
  id uuid primary key,
  user_id uuid not null unique references app_user(id),
  full_name varchar(160),
  headline varchar(200),
  current_role varchar(160),
  experience_years numeric(4,1),
  location varchar(160),
  phone varchar(40),
  portfolio_url varchar(500),
  bio text,
  profile_completion smallint not null default 0,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table guest_session (
  id uuid primary key,
  browser_session_key varchar(160) not null unique,
  candidate_id uuid references candidate(id),
  status varchar(20) not null default 'active',
  last_activity_at timestamptz not null default now(),
  expires_at timestamptz not null,
  created_at timestamptz not null default now()
);

create table cv_document (
  id uuid primary key,
  candidate_id uuid references candidate(id),
  guest_session_id uuid references guest_session(id),
  original_file_name varchar(500) not null,
  storage_key varchar(700),
  mime_type varchar(120) not null,
  file_size_bytes bigint not null,
  page_count integer,
  upload_status varchar(20) not null,
  parse_status varchar(20) not null default 'pending',
  uploaded_at timestamptz not null default now(),
  parsed_at timestamptz,
  check (candidate_id is not null or guest_session_id is not null)
);

create table cv_parse_result (
  id uuid primary key,
  cv_document_id uuid not null unique references cv_document(id),
  parser_version varchar(60) not null,
  candidate_name varchar(160),
  email varchar(320),
  phone varchar(40),
  headline varchar(200),
  summary text,
  skills jsonb not null default '[]',
  work_history jsonb not null default '[]',
  education jsonb not null default '[]',
  extracted_keywords jsonb not null default '[]',
  raw_payload jsonb not null default '{}',
  created_at timestamptz not null default now()
);

create table candidate_preferences (
  id uuid primary key,
  candidate_id uuid references candidate(id),
  guest_session_id uuid references guest_session(id),
  target_role varchar(160) not null,
  experience_band varchar(20) not null,
  preferred_location varchar(160) not null,
  work_mode varchar(20),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  check (candidate_id is not null or guest_session_id is not null)
);

create table cv_analysis (
  id uuid primary key,
  candidate_id uuid references candidate(id),
  guest_session_id uuid references guest_session(id),
  cv_document_id uuid not null references cv_document(id),
  target_role varchar(160) not null,
  status varchar(20) not null default 'pending',
  score numeric(5,2) not null default 0,
  max_score numeric(5,2) not null default 100,
  score_label varchar(20),
  projected_score numeric(5,2),
  criteria jsonb not null default '[]',
  positives jsonb not null default '[]',
  negatives jsonb not null default '[]',
  recommendations jsonb not null default '[]',
  parser_version varchar(60),
  analysis_version varchar(60) not null,
  created_at timestamptz not null default now(),
  completed_at timestamptz
);

create table interview_session (
  id uuid primary key,
  candidate_id uuid not null references candidate(id),
  cv_analysis_id uuid references cv_analysis(id),
  role varchar(160) not null,
  interview_type varchar(30) not null,
  status varchar(20) not null default 'created',
  question_count integer not null default 0,
  started_at timestamptz,
  completed_at timestamptz,
  created_at timestamptz not null default now()
);

create table interview_answer (
  id uuid primary key,
  interview_session_id uuid not null references interview_session(id),
  question_id varchar(120) not null,
  question_text text not null,
  answer_mode varchar(20) not null,
  answer_text text not null,
  transcript_status varchar(20) not null,
  audio_storage_key varchar(700),
  duration_seconds integer,
  answered_at timestamptz not null default now()
);

create table interview_analysis (
  id uuid primary key,
  interview_session_id uuid not null unique references interview_session(id),
  overall_score numeric(5,2) not null,
  communication_score numeric(5,2),
  technical_score numeric(5,2),
  structure_score numeric(5,2),
  strengths jsonb not null default '[]',
  improvements jsonb not null default '[]',
  answer_feedback jsonb not null default '[]',
  analysis_version varchar(60) not null,
  created_at timestamptz not null default now()
);

create index idx_cv_document_candidate on cv_document(candidate_id, uploaded_at desc);
create index idx_cv_analysis_candidate on cv_analysis(candidate_id, created_at desc);
create index idx_interview_candidate on interview_session(candidate_id, created_at desc);
create index idx_answer_session on interview_answer(interview_session_id, answered_at);
```

## 6. Guest-to-user merge transaction

When OTP verification succeeds:

1. Find or create `app_user` by normalized email.
2. Find or create the one-to-one `candidate` record.
3. Read the active `guest_session` from the browser session key.
4. Attach guest CV documents, preferences, and CV analyses to `candidate_id`.
5. Update `guest_session.status` to `claimed`.
6. Reconcile parsed CV fields with existing profile fields. Parsed values should fill empty fields and should not overwrite user-edited values without explicit consent.
7. Return an authenticated session and the complete candidate summary.

This operation must be idempotent. Retrying the login request must not duplicate CV documents, analyses, or candidate profiles.

## 8. Frontend mock implementation mapping

Until APIs are available, implement repositories with the same method names:

```ts
interface CandidateRepository {
  getCurrentCandidate(): Promise<Candidate | null>;
  saveCandidate(candidate: Candidate): Promise<Candidate>;
  mergeGuestSession(input: { guestSessionId: string; userId: string }): Promise<Candidate>;
}

interface CvRepository {
  createGuestSession(): Promise<GuestSession>;
  uploadDocument(input: UploadCvInput): Promise<CvDocument>;
  getParseResult(documentId: string): Promise<ParsedCvResult | null>;
  savePreferences(input: CandidatePreferences): Promise<CandidatePreferences>;
  getAnalysis(analysisId: string): Promise<CvAnalysis>;
}

interface InterviewRepository {
  createSession(input: CreateInterviewInput): Promise<InterviewSession>;
  saveAnswer(input: InterviewAnswer): Promise<InterviewAnswer>;
  completeSession(id: string): Promise<InterviewAnalysis>;
  listCandidateInterviews(candidateId: string): Promise<InterviewSession[]>;
}
```

The local implementation should use one versioned storage key, for example `welhire.mock.v1`, rather than scattering independent values throughout components. The authenticated user key may remain `welhire-demo-user` during the transition, but it should eventually be represented by the mock auth repository.

## 9. State rules

- A guest may upload and receive a basic CV score without logging in.
- Detailed profile history requires an authenticated candidate.
- Every CV and analysis must retain its source `cvDocumentId`.
- Every interview must retain its `candidateId` and optional `cvAnalysisId`.
- User-edited profile values have priority over parsed values.
- Completed analysis and interview records are immutable; corrections create a new version.
- All list endpoints should be ordered by newest first and support pagination.
- Local storage is only a development substitute and must not be treated as secure authentication.

## 10. Implementation order

1. Add shared TypeScript domain types.
2. Add versioned mock database and repository interfaces.
3. Move current `CvAnalysisContext` values into the mock repositories.
4. Add guest session creation at CV analysis entry.
5. Persist upload, parsed details, preferences, and analysis results.
6. Connect OTP login to guest-session merge.
7. Replace hard-coded header/profile values with the candidate store.
8. Persist interview sessions and answers.
9. Build interview analysis and profile history from repository data.
10. Replace mock repository methods with Java service clients when APIs are ready.
